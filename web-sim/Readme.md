# 六轴机械臂仿真 —— B/S 版本（独立子项目）

本目录是与仓库根目录下 **VTK 桌面版**（`六轴机械臂仿真.sln`）并存的另一套实现：
把运动学计算放到 C++ 后端，渲染与交互交给浏览器（Three.js / WebGL），
可用浏览器直接访问，也可以用 Electron 套成桌面应用。

> 两套实现共用同一套 DH 参数与逆解思路，运动学数值行为一致（根目录 `Robot.h` ⇄ 本目录 `RobotCore.h`）。
> 本目录完全是新增内容，**不影响根目录工程的编译**。

```
┌────────────────────┐  POST /api/command   ┌──────────────────────────┐
│ 前端（浏览器/Electron）│ ──────────────────▶ │  后端 RobotServer (C++)   │
│ Three.js + WebGL    │ ◀────────────────── │  RobotCore / RobotUtils  │
└────────────────────┘  SSE /api/stream     └──────────────────────────┘
```

## 快速开始

### 1. 编译后端

```powershell
# 在 Visual Studio 中打开本目录的 RobotServer.sln，选 Release | x64 编译
# 或命令行：
& "<MSBuild路径>\MSBuild.exe" RobotServer.vcxproj `
    /p:Configuration=Release /p:Platform=x64 /t:Build `
    /p:OutDir="$((Resolve-Path .).Path)\x64\Release\"
```

产物为 `web-sim\x64\Release\RobotServer.exe`。

> 只需要 Eigen 头文件，工程里 `EigenRoot` 默认指向 PCL 自带的 `3rdParty\Eigen`；
> 如果 Eigen 在别处，改 `RobotServer.vcxproj` 里这一行即可。

### 2. 运行

**浏览器方式**（后端同时托管前端页面）：

```powershell
pwsh -File scripts\run.ps1          # 缺少产物时会自动编译
# 然后浏览器打开 http://127.0.0.1:8760/
```

**桌面端方式**（Electron 会自动拉起后端）：

```powershell
cd desktop
npm start
```

**前后端分开启动**（两个终端，各自独立）：

```powershell
# 终端 1：只启动后端
cd web-sim
.\x64\Release\RobotServer.exe --port 8760 --web web

# 终端 2：只启动前端窗口，连接上面那个后端（不会再拉起后端，退出时也不会关掉它）
cd web-sim\desktop
npm run frontend
```

| 命令 | 作用 |
|:---|:---|
| `npm start` | 前端窗口 + 自动拉起后端（退出时一并关闭） |
| `npm run frontend` | 只开前端窗口，连接已经在运行的后端 |
| `npm run dev` | 同 `npm start`，额外输出 Chromium 日志 |
| `ROBOT_PORT` 环境变量 | 前后端约定的端口，默认 8760 |

> Electron 的三个脚本都带 `--no-sandbox`：Chromium 的沙箱在受限终端里初始化失败时，
> Electron 会在加载 `main.js` 之前就静默退出（退出码 `0x80000003`，控制台一个字都不打印、
> 窗口也不出现）。若你的环境不需要，把 `desktop\package.json` 里的 `--no-sandbox` 删掉即可。

> 在 **VS Code 集成终端**里启动时，请先关掉 JS 调试器的自动附加（状态栏 `Auto Attach` → Off，
> 或设置 `debug.javascript.autoAttachFilter: "disabled"`）：它会注入 `NODE_OPTIONS` /
> `VSCODE_INSPECTOR_OPTIONS`，让 Electron 主进程卡在 `inspector.waitForDebugger()` 上，
> 症状同样是「没有任何输出、窗口不出现」。

也可以手动启动（只开后端）：

```powershell
.\x64\Release\RobotServer.exe --port 8760 --web web
```

### 3. 端到端验证

pwsh -File scripts\verify.ps1

会用真实 Chromium 打开前端，检查页面加载、WebGL 渲染、状态送达、交互生效，

## 前端功能

左侧控制面板：

1. **目标位置**：直接输入 X / Y / Z，回车或点「应用坐标」生效；
2. **末端姿态**：两个滑块给出目标坐标系 Z 轴方向的 X / Y 分量，剩余分量自动补齐并归一化；
3. **位置微调**：三个增量滑块，拖动时持续发送增量，松手自动归零；
4. **操作**：载入点云包围盒目标、**随机点云目标**（位置与姿态随机）、**隐藏/显示目标**
   （一键收起目标点云与包围盒）、回到零位、显示/隐藏点云、显示/隐藏轨迹、重置视角、
   坐标轴开关、轨迹采样点数量，以及**新旧逆解算法对比开关**；
5. **传送带取件场景**：启动/暂停/复位，传送带速度与生成间隔可调，可开关「托盘满后自动清空」，
   面板上实时显示当前阶段、已抓取数、已码放数与在带数量；任何手动操作会自动暂停场景；
6. **关节角微调**：每个关节一个滑块，直接按正运动学更新末端位姿，并提供「回放当前轨迹」；
7. **显示选项**：工具坐标系、目标坐标系、地面网格、点云、包围盒开关。

右侧三维视图：鼠标左键旋转、右键平移、滚轮缩放；右上角浮层实时显示末端位置、目标位置、位置误差与六个关节角。

目标**不可达**（逆解无解）时，状态栏给出「逆解无解，机械臂保持原位」提示，橙色目标框停在用户
输入的位置、机械臂停在原位不动；随后输入任意可达坐标即可继续，不需要先「回到零位」。

## 运动学约定

DH 变换矩阵（与根目录 `Robot.h` 一致）：

$$
R =\left[\begin{matrix}
	\cos{\theta}&-\sin{\theta} &0\\
	\cos{\alpha}\sin{\theta} & \cos{\alpha}\cos{\theta} & -\sin{\alpha}\\
	\sin{\alpha}\sin{\theta}&\sin{\alpha}\cos{\theta}&\cos{\alpha}\\
\end{matrix}\right],\quad
T = \left[\begin{matrix} a & -d\sin{\alpha} & d\cos{\alpha} \end{matrix}\right]^T,\quad
H = \left[\begin{matrix} R & T\\ 0 & 1 \end{matrix}\right]
$$

使用的机械臂为 **博朗特 BRTIRUS0805A**（`RobotUtils::createDefaultRobot`）：

| 轴 | a | α(°) | d | θ(°) |
|:---:|:---:|:---:|:---:|:---:|
| 1 | 0 | 0 | 155.5 | 0 |
| 2 | 75.95 | 90 | 7.05 | 90 |
| 3 | 390 | 0 | 0 | 0 |
| 4 | 117.5 | 90 | 394 | 0 |
| 5 | 0 | 90 | 0 | 0 |
| 6 | 0 | -90 | 0 | 0 |
| 工具 | 0 | 0 | 119 | 0 |

**逆解（完备解析解，最多 8 组）**

本模型用的是**改进 DH**：$H_i = Rot_x(\alpha_i)\,Trans_x(a_i)\,Rot_z(\theta_i)\,Trans_z(d_i)$。
轴 4、5、6 的平移量都是 0，所以这三根轴交于同一点（球形手腕），于是可以解析地拆成
「位置（θ1θ2θ3）+ 姿态（θ4θ5θ6）」两步，解是有限的多组：

```
                肩部 ±1  ×  肘部 ±1  ×  腕部 ±1  =  最多 8 组
```

求解步骤（全部用 `atan2`，不用 `acos`，因此在 ±180° 附近连续）：

1. **腕心** $W = TCP - 119\cdot z_{tool}$，即轴 4/5/6 的交点；
2. **θ1**：$p_1 = R_1^{\mathsf T}(W - t_1)$ 的 y 分量恰好等于肩部偏置 $d_2$，
   于是 $\theta_1 = \varphi - \operatorname{atan2}(d_2, p_{1x})$，其中 $\varphi=\operatorname{atan2}(W_y,W_x)$，
   $p_{1x}=\pm\sqrt{r^2-d_2^2}$（肩部两个分支）；
3. **θ3**：由腕心到轴 2 原点的距离反解 $A_3=\dfrac{p_x^2+q^2-a_3^2-r_4^2}{2a_3}$，
   $B_3=\pm\sqrt{r_4^2-A_3^2}$（肘部两个分支），再由
   $\begin{bmatrix}A_3\\B_3\end{bmatrix}=\begin{bmatrix}a_4&-d_4\\d_4&a_4\end{bmatrix}
   \begin{bmatrix}\cos\theta_3\\\sin\theta_3\end{bmatrix}$ 解出 θ3；
4. **θ2**：由 $\begin{bmatrix}p_x\\q\end{bmatrix}=\begin{bmatrix}u&-v\\-v&-u\end{bmatrix}
   \begin{bmatrix}\cos\theta_2\\\sin\theta_2\end{bmatrix}$ 解出（$u=a_3+A_3,\ v=B_3$）；
5. **θ4θ5θ6**：令 $R_{36}=R_{03}^{\mathsf T}R_{target}$，则
   $\cos\theta_5=R_{36}(1,2)$，θ5 取 ±两个分支，
   $\theta_4=\operatorname{atan2}(-R_{36}(2,2)/s_5,\ R_{36}(0,2)/s_5)$，
   $\theta_6=\operatorname{atan2}(R_{36}(1,1)/s_5,\ -R_{36}(1,0)/s_5)$；
   $s_5\approx0$ 的奇异位形下 θ4 与 θ6 只以「和/差」出现，取参考构型的 θ4 再补出 θ6；
6. **自校验**：每一组候选都用正解回代，只有位置误差 < 0.1 mm、姿态误差 < 2e-3 的解才返回；
7. **选解**：把各组解按 ±2π 折算到**参考构型**附近，取关节变化最小的一组。
   参考构型默认是当前关节角，因此连续给点时解也连续。

> 之前那一版只给出「肩部单分支 + 肘部 `-acos` 单分支 + 姿态 acos 加符号判据」的**一组特解**，
> 于是两个毛病：大量几何上可达的目标被判成不可达（可达区域呈碎片状）；θ4/θ6 在 ±180° 附近
> 符号判据会翻转，竖直向下运动时相邻两点解出 +180° 与 −180° 两种等价解，
> 插值时就表现为「姿态突然转 360°」。旧实现已备份在 `_backup/` 目录下。

**新旧算法对比开关**：面板第 4 节勾选「使用旧逆解（单分支特解）」即可切回旧算法
（等价于 `POST /api/command {"action":"setIKMode","mode":"legacy"}`），状态帧的
`model.ikMode` 会给出当前值。两种算法的差别可以这样观察：

| 观察项 | 完备解析解（默认） | 旧特解 |
|:---|:---|:---|
| 可达区域 | 完整（竖直扫描 96/96 点可解） | 碎片状（例如 (420,0) 整列不可解） |
| 竖直下降连续性 | 相邻点最大变化 8.8° | 可能出现 ±180° 翻转（等效 360°） |
| 同一目标的解 | 在最多 8 组里按参考构型就近选 | 固定一组，姿态可能与预期不同 |
| 解的正确性 | 每组都做正解回代校验 | 不校验 |

切到旧算法时场景仍能跑，但工位预解算可能失败或解出翻转的关节角，属于预期现象。

**不可达时不写回**：`IK` 是「全有或全无」的，解不出来就返回 `false` 并保持关节角原样，
绝不会把 NaN 写进模型（否则之后**任何**目标都会继续解出 NaN，状态帧里的数值全变成 `null`）。

**末端朝向修正**：若目标坐标系的 Z 轴指向机械臂本体，则把它取反 —— 同时取反 X 轴
（相当于绕 Y 轴转 180°），保证仍是右手系；只取反 Z 会让旋转矩阵行列式变成 −1，
那就不是合法位姿了。

> 关节角在内部统一使用弧度；对外（界面与接口）使用角度制，
> 符号约定与 DH 参数表一致：初始置零时 α、θ 均取自 DH 表。

## 机械臂是独立实体（可任意增删）

后端不再把机械臂写死成「左臂 / 右臂」，而是 `RobotService` 持有一组机械臂实体，
每台臂带 `ID` 与 `Name`，**所有设置都是每臂独立的**：

| 每台臂自己的东西 | 说明 |
|:---|:---|
| `ID` / `Name` | 前端用它区分、操作各台臂；编号稳定，删掉别的臂也不会串号 |
| 逆解模式 | 完备解析解 / 旧特解，每台臂各自选择 |
| 速度系数 | 20%~300%，只影响这一台 |
| 轨迹采样点数 | 4~200，只影响这一台的 `getTrack` 规划分辨率 |
| 跟踪速度上限 | 动态抓取时这台臂的最大关节角速度 |
| 基座位姿 | 世界坐标 (x, y)，可以在界面上随时挪动 |
| 收集台 | 垛位按基座推导（横向朝带面靠 150mm，纵向 -480/-230），跟着臂走 |
| 统计与轨迹 | 抓取/码放/漏抓、本周期 TCP 轨迹、`getTrack` 规划轨迹各自一套 |

场景里的**分工按「离货物最近的机械臂」**自动划分：两台臂时正好等价于按带面中心线分左右，

## 抓取工位与货物锁（多机械臂协同）

每台机械臂都有**自己的抓取工位**（传送带上的 Y 坐标，面板「6. 机械臂管理」里可单独设定），
货物路过谁的工位，谁才有机会抓 —— 于是天然形成「上游没抓到、下游接着抓」的流水线。

### 抓取申请与货物锁

一件货物在传送带上同一时刻**只能被一台臂认领**，靠 `Box::claimedBy` 一个字段实现互斥：

```
臂空闲 → 在自己工位窗口内找货(最靠前的一件)
      → requestBox() 发出抓取申请
           ├─ 没人认领  → 上锁(claimedBy = 我)，claimed++，开始取件
           ├─ 已经是我  → 继续
           └─ 别人锁着  → contended++，放弃这一件（退回待命，稍后再看）
      → 解不出抓取位 / 追不上 / 等太久 → releaseBox() 解锁，让货物继续流向下游工位
```

- **定点模式**：被认领的货物停到**认领者的**工位（含各自的停位抖动）；没被认领的继续往前走；
  带面上有「前车限位」，被挡停的货物不会让后面的追尾。
- **动态模式**：货物不停，认领只决定「谁来追」，抢不到锁的臂直接放弃。
- 申请被拒后有 0.5s 退避；同一件解不出来的货会记进 `skipBoxId`，不再反复申请。
- `claimedBy` 对**传送带上的货**是锁，对**已抓起/已码放的货**是归属：只有传送带上的箱子
  才能被 `releaseBox/releaseClaims` 解锁，码好的箱子永远归属那台臂 ——
  「托盘满后自动清空」「移动基座」「删除臂」都靠它认出自己的货。

面板上每台臂都会显示 `工位 y=…　抢锁 N 成/M 拒　锁着 #id`，抢锁过程直接可见。

| 指令 | 参数 | 作用 |
|:---|:---|:---|
| `setArmPickY` | `arm, y` | 设定这台臂的抓取工位（传送带 Y），越界的会夹到带内 ±200mm |

自检里的抢锁验证（两台臂工位都设到 y=0、一次只来一件货）：

```
--- 货物锁（工位重叠时的抢锁）---
  机械臂： 抓取 4，码放 4，申请成功 4，被拒 0
  机械臂： 抓取 0，码放 0，申请成功 0，被拒 24
抢锁被拒总次数： 24（>0 说明「申请—被拒—放弃」协议真的在起作用）
同一件货物被两台臂同时锁定的帧数： 0（必须为 0）
两台臂合计码放： 4 件
```

默认两台臂的工位是错开的（左臂 y=+250 在下游、右臂 y=-250 在上游），
所以默认演示就是一条两级流水线；把两个工位设成一样就能看到抢锁。

### 运动轨迹显示（算法对比用）

每台臂都会记录**本周期**的末端轨迹（从离开待命位开始，到回到待命位为止，50Hz 采样、
最多 600 点），在三维视图里用各自的主色画成折线（左臂青蓝、右臂橙），
并在对比卡片里给出两个量化指标：

| 指标 | 含义 | 为什么有用 |
|:---|:---|:---|
| 轨迹总长 | 本周期末端走过的路程 | 同样的搬运任务，路径越长说明绕得越多 |
| 最大跳变 | 相邻采样点之间的最大距离 | 逆解发生分支跳变/翻转时会突然出现大跳变 |

实测对比（同样的搬运任务）：左臂（完备解）一个周期约 **1.6~2.5 m**，
右臂（旧特解）经常达到 **6.5 m** 并在视图里画出明显的大回环 —— 这正是两种算法
在「同一个世界位姿该给哪组关节角」上的差别。

#### 分段轨迹由谁规划

场景里每一段运动（去取件位 / 下降 / 提升 / 搬运 / 下放 / 返回）都有两种规划方式，
**按该臂的逆解模式自动选择**：

| 臂的逆解模式 | 规划方式 | 说明 |
|:---|:---|:---|
| 旧特解（legacy） | **`Robot::getTrack`** | 调 `planTrack(目标关节角)` 拿到插值好的关节序列，再按时间比例**逐点执行** |
| 完备解析解（complete） | 场景内置插值 | 关节空间 smoothstep 加减速（`beginMove` / `advanceMove`） |

所以旧特解臂上「规划出来的轨迹」与「实际走出来的轨迹」是**同一条**（不是记一套、走另一套），
`Robot::getTrack` 里加的调试输出也会在场景运行时正常刷出来。

视图里对应两条线：

- **实线** = 实际走出来的（每帧采样的 TCP，`arms[].path`）
- **虚线** = `getTrack` 规划出来的当前这一段（`arms[].planned`，共 `trackSize` 个点）

#### 两个调节旋钮

面板第 5 节（第 4 节也有一个同步的轨迹采样点滑条）：

| 旋钮 | 范围 | 作用 |
|:---|:---|:---|
| **轨迹采样点** | 4 ~ 200（默认 24） | `getTrack` 每段插值多少个点。点数少时旧特解臂每段只有寥寥几个离散姿态，动作会"咯噔"；拉到 100~200 明显连续 |
| **机械臂速度** | 20% ~ 300%（默认 100%） | 乘在每段运动的关节角速度上（`moveDuration = 最大关节角变化量 / 角速度`），也同时缩放动态抓取的跟踪速度上限 |

> 注意：轨迹点数只影响**分辨率**（旧特解臂逐点执行的粒度 + 轨迹线的密度），不改变每段运动的时长；
> 想让整体节拍变快，调「机械臂速度」。两者独立，可以组合出「高分辨率 + 快节拍」的演示效果。

> 动态抓取（跟踪移动货物）用的是按速度限幅的连续跟踪（`steerTo`），
> 无法用 `getTrack` 的分段插值，因此两种模式在跟踪阶段都走 `steerTo`。

**抓取是按货物实际坐标解算的**（不是「走到固定工位吸附一下」）：

1. 货物滑到自己的挡停位后，取它的**实际坐标** $(x,y)$ 与上表面高度 $z$；
2. 用 `solveIK(位姿, 参考构型=当前关节角)` 现解抓取位与接近位 ——
   即以「离当前姿态最近」的那组解为准，因此动作幅度最小；
3. 万一该坐标解不出来，就在横向 ±12/±20 mm、纵向 ±10 mm、高度 +8/+16 mm 的小范围里试探
   （夹爪本来就有一定容差），全都失败才记一次「漏抓」并跳过这一箱；
4. 实测抓取时末端与货物的水平偏差 **0.0~1.1 mm**，横向偏移覆盖 ±60 mm 以上。

### 两种抓取模式

面板第 5 节的「**抓取移动中的货物**」勾选框切换：

| | 定点抓取（默认） | 动态抓取 |
|:---|:---|:---|
| 货物行为 | 滑到挡停线**停稳**，后面排队 | **不停**，匀速通过取件窗口 |
| 机械臂 | 走到货物停位上方，`MoveJ` 插值下去抓 | **预测 + 跟踪**：算出「现在出发、到达时货物在哪」，再全程跟随 |
| 运动控制 | 分段关节空间插值（smoothstep 加减速） | 每帧按最大关节角速度**朝移动目标赶**（可随时换目标，天然连续） |
| 合爪判据 | 下降到位即合爪 | 末端与货物的**水平偏差 + 高度**都进入容差才合爪 |
| 追不上时 | —— | 货物越过 `pickY + 260mm` 记为漏抓，机械臂回待命位 |

**运动预测**的做法是一个三步不动点迭代：先假设一个行程时间 $t$，算出「那时货物在哪」并解一次逆解，
用该解与当前关节角的差反推更准的 $t$，迭代 3 次。据此决定**什么时候出发**：
到达时货物恰好进入取件窗口就出发，太早就继续等，太晚（已经追不上）就留给下一箱。

自检里的动态抓取结果（传送带 200 mm/s）：

```
--- 动态抓取（货物不停机）---
抓取件数： 4，码放件数： 4，漏抓： 1
跟踪偏差： 平均 12.5 mm，最大 22.9 mm（传送带 200 mm/s）
```

**抓取约定**：工具末端（TCP）对准的是纸箱的**上表面**，不是箱子中心 ——
夹爪从法兰出来 119 mm 到 TCP，两指再从 TCP 往下包住箱子两侧（指长取箱高的 3/4，
这样既夹得住又不会戳到带面/台面）。被夹持的箱子中心 = TCP 沿工具 Z 轴方向再往下半个箱高。

实现上有三点值得说明：

1. **工位预解算**：场景复位时用 `Robot::solveIK`（只解算、不写回）把所有工位解一遍，
   解不出来就进入「故障」状态并给出原因，绝不会把 NaN 写进关节；
2. **关节空间插值**：机械臂在工位之间做 `MoveJ` 式的平滑插值（smoothstep 加减速），
   中途不调用逆解 —— 本机型的逆解只在特定位置可解（可达区域有「空洞」），
   逐点笛卡尔跟踪会频繁失败，而关节空间插值天然不会；
3. **前后端分工不变**：传送带、箱子、垛位、夹爪开合度全部由后端算好写进状态帧，
   前端只按 `scenario.boxes` 摆方块、按夹爪张开度画两根手指。

> 关于「工具」的渲染：`Robot::getJointH(index)` 返回的关节坐标系**不含工具**，
> `index == 6` 就是第 6 轴法兰（也就是工具安装面）。因此状态帧里最后一个关节位置是法兰，
> 前端把「法兰 → TCP」这 119 mm 画成夹爪本体，而不是画成又一根机械臂连杆。
